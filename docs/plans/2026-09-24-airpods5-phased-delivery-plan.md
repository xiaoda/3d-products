# AirPods 5 分阶段实施与验收计划

> 执行约定：使用 `executing-plans` 技能按阶段推进；每阶段完成后先提交成果与证据，用户验收通过后才进入下一阶段。当前阶段一开发与自测已完成、待用户验收，其余阶段未开始；计划内容本身不代表验收通过。

**目标：** 通过六次可独立验收的增量交付，完成纯 Three.js 程序化建模的 AirPods 5 高还原交互展示网页。

**架构：** 使用静态单页，分离参数配置、模型生成、场景渲染、交互状态与页面界面。沿用同一产品节点结构逐步精修，每个阶段都在上一阶段可运行成果上增加能力，不另建互不兼容的演示项目。

**技术栈：** Vite、TypeScript、Three.js、原生 HTML/CSS、Vitest、浏览器测试；本地视觉验证优先使用 Chrome DevTools MCP。

**设计依据：** [AirPods 5 网页 3D 产品展示开发方案](./2026-09-24-airpods5-3d-showcase-design.md)。

## 一、总览与验收机制

| 阶段 | 用户可直接看到或操作的成果 | 预计工作量 | 当前状态 |
| --- | --- | --- | --- |

| 2 | 外形和主要细节完整的精修灰模 | 3–5 天 | 未开始 |

预计开发工作量合计 8–14 个工作日，不含等待用户验收、补充资料和新增需求的时间。

### 1.1 通用交付包

每个阶段结束时提供：

1. **可运行成果**：本地源码与实际确认过的 HTTP 预览地址；服务停止后可按运行说明重新启动，地址不是永久在线链接。
2. **操作说明**：3–5 个用户可直接执行的验收步骤。
3. **截图证据**：实际浏览器截图，而不是设计稿或未运行代码的推测。
4. **测试记录**：通过、失败、未验证项分别记录，不能把未验证写成通过。
5. **已知限制**：明确本阶段尚未实现的内容，避免将后续功能误认成缺陷。
6. **版本记录**：记录本阶段源码状态；使用 Git 后保存提交标识，不能覆盖用户未提交修改。

### 1.2 阶段通过标准

- 技术验收：该阶段检查项通过，没有阻止主要操作的缺陷。
- 视觉验收：用户确认该阶段负责的比例、形体或质感。自动化测试不能替代审美判断。
- 阶段结论：记录为“待验收”“通过”或“需修改”，注明用户反馈。
- 阶段一只批准粗比例与架构；阶段二才批准精修几何形体。
- 每阶段停止点清晰，未经本阶段验收确认，不主动继续下一阶段。

### 1.3 执行方法与命令约定

以下命令已在阶段一建立；实际执行结果见 `docs/acceptance/stage-01.md`，不要将阶段一结果视为后续阶段也已通过：

```powershell
npm run dev -- --host 127.0.0.1
npm run typecheck
npm run test -- --run
npm run build
npm run preview -- --host 127.0.0.1
```

- 对几何工具、状态转换和导出尺寸计算，按“写失败测试 → 运行确认失败 → 最小实现 → 运行确认通过 → 重构”的顺序开发。
- `typecheck` 应无类型错误；单元测试应全部通过；构建应成功产生 `dist/`。
- 浏览器检查必须实际加载页面、读取快照并查看截图，不能只运行构建命令。
- 小功能完成后保存版本；不要为本任务强行初始化、改写或清理未知 Git 历史。
- 分阶段记录具体执行命令和结果；纯渲染外观通过固定视角截图和人工对照验收。

## 二、阶段一：工程与基础白模

### 目标与前置条件

让项目先在本地浏览器里运行起来，出现充电盒、盒盖和左右耳机的基础白模，并能旋转、缩放。

实施开始时确认一个具体产品版本，收集正面、侧面、背面和开盖参考。缺少某视角时明确记录，不把猜测当成已知结构。

### 开发任务与文件

1. 创建 `package.json`、锁文件、`index.html`、`tsconfig.json`、`vite.config.ts`，配置启动、检查、测试和构建脚本。
2. 创建 `src/config/product.ts`，集中保存单位、尺寸和产品版本。
3. 创建 `src/scene/createScene.ts`、`src/main.ts`，建立渲染器、相机、基础灯光与尺寸响应。
4. 创建 `src/model/createProduct.ts`、`src/model/createCase.ts`、`src/model/createEarbud.ts`，形成稳定节点结构和粗白模。
5. 创建 `src/ui/controls.ts`、`src/ui/styles.css`，提供简单操作提示与视角重置。
6. 创建 `src/tests/product.test.ts`，验证必要节点、尺寸参数与有效包围盒。
7. 创建 `docs/reference-manifest.md`、`README.md`，记录参考来源、所选版本和启动方式。

### 可验收成果

- 一个可访问的本地展示页，不是空 Canvas 或只显示测试立方体。
- 灰白色充电盒、盒盖和左右耳机；为了看清三个主体，提供一个固定分开展示姿态。
- 鼠标旋转、缩放、重置视角。
- 正面、侧面、顶部三张基础白模截图。

### 用户验收步骤

1. 打开预览地址，确认产品完整显示。
2. 拖动模型查看不同方向，滚轮缩放后点击重置。
3. 对照参考检查盒体与耳机的整体比例。
4. 缩窄浏览器，确认模型仍可见且画面比例正常。

### 通过标准

- [ ] 盒体、盒盖、左耳机、右耳机均存在，且节点可独立控制。
- [ ] 旋转和缩放正常，缩放受限，不能轻易进入模型内部。
- [ ] 改变窗口尺寸后画面不拉伸，主体不意外消失。
- [ ] 尺寸配置、包围盒测试和生产构建通过，无阻断运行的控制台错误。
- [ ] 用户认可基础比例与部件位置，接受其为粗白模而非最终外形。

### 本阶段不做

最终耳机曲面、精细开孔、真实材质、完整开合动画和正式页面设计。

**停止点：提交阶段一预览、三视图截图和 `docs/acceptance/stage-01.md`，等待验收。**

## 三、阶段二：高还原几何模型

### 目标与前置条件

阶段一通过后，把粗白模替换为参数化精修曲面；即使使用统一灰色材质，也能从主要方向辨认出目标产品形体。

### 开发任务与文件

1. 创建 `src/model/geometry.ts` 和 `src/tests/geometry.test.ts`，先验证截面连接、索引范围和法线，再实现曲面生成工具。
2. 精修 `src/model/createCase.ts`，实现盒体曲面、盒盖内侧、内胆、耳机槽与铰链节点。
3. 精修 `src/model/createEarbud.ts`，实现非对称耳机头部、耳机柄和连续过渡。
4. 更新 `src/config/product.ts`，加入曲面控制参数、装配姿态和细节位置。
5. 创建 `src/model/details.ts`，制作接口、传感器、网罩边缘和金属触点等主要细节。
6. 创建仅开发模式使用的 `src/debug/modelInspection.ts`，提供固定视角、线框与静态开盖角度检查；不作为正式用户交互。
7. 扩展 `src/tests/product.test.ts`，检查关键尺寸和部件层级；保留统一灰色材质进行形体评审。

### 可验收成果

- 可旋转的精修灰模，包含开盖后能看到的内胆与收纳槽。
- 闭合、开盖、耳机分开展示三个静态检查姿态。
- 正面、侧面、背面、顶部、开盖内部、单耳特写六组截图。
- 关键参考图与对应模型视角的对照记录。

### 用户验收步骤

1. 切换固定视角，对比耳机头部、柄长与盒体轮廓。
2. 查看耳机头部与柄的衔接处，检查是否有明显拼接台阶。
3. 查看开盖内部及铰链位置，确认结构关系合理。
4. 在开发检查界面改变盒盖角度，检查盒盖和盒体有无明显碰撞。
5. 查看耳机收纳姿态与单耳特写。

### 通过标准

- [ ] 所有主体几何由 Three.js 程序化生成，没有导入外部产品模型。
- [ ] 六组视角均无明显破面、孔洞、法线翻转或不应存在的接缝。
- [ ] 耳机头部和柄的过渡自然，不是可见的球体与圆柱体拼接。
- [ ] 内胆具有槽壁与深度，盒盖绕铰链检查时结构关系正确。
- [ ] 收纳姿态下无明显穿模；主要细节与选定版本参考一致。
- [ ] 关键尺寸相对配置值的偏差控制在约定容差内，默认不超过 1%；该容差仅约束数字尺寸，不表示实物曲面还原率。
- [ ] 用户确认精修形体可以进入材质阶段。

### 本阶段不做

摄影棚最终灯光、产品营销页面和正式动画时间线。缺少依据的内部电子结构不制作成“真实拆解”。

**停止点：形体未通过时继续本阶段修模，不用材质高光掩盖问题。**

## 四、阶段三：材质、灯光与展示构图

### 目标与前置条件

阶段二形体验收通过后，把灰模制作成具备白色塑料、金属和网罩质感的产品展示。

### 开发任务与文件

1. 创建 `src/model/materials.ts`，分离外壳、金属、深色传感器和网罩材质。
2. 创建 `src/scene/lighting.ts`，配置摄影棚环境反射、主辅光与柔和阴影。
3. 更新 `src/scene/createScene.ts`，统一色彩、曝光和背景设置。
4. 创建 `src/scene/cameraPresets.ts`，定义闭合、开盖、单耳特写等固定构图。
5. 将需要的纹理放入 `public/textures/`，在 `docs/asset-manifest.md` 记录来源和许可情况。
6. 保留开发模式灰模开关，方便排查几何与材质问题。

### 可验收成果

- 支持自由旋转的真实感产品展示页。
- 至少三张实际浏览器截图：闭合主视觉、开盖双耳展示、单耳特写。
- 可重复使用的材质、灯光和相机预设。

### 用户验收步骤

1. 查看主视觉，判断白色外壳是否有体积与层次。
2. 旋转产品，观察高光是否平滑移动，是否暴露形体缺陷。
3. 查看金属、网罩和外壳的区别。
4. 切换到背面和特写，检查曝光和反射是否仍然合理。

### 通过标准

- [ ] 外壳、金属、网罩能够通过材质清楚区分。
- [ ] 白色外壳不过曝，分件缝隙与主要曲面仍可辨认。
- [ ] 多视角下不存在明显闪烁、材质丢失或不合理黑面。
- [ ] 阴影自然，不存在明显悬浮贴图感或重叠表面闪烁。
- [ ] 模型旋转时高光连续，不能仅在一个指定角度看起来正确。
- [ ] 用户确认主视觉构图与材质方向。

### 本阶段不做

最终营销排版、完整动作流程和用户图片导出。此阶段截图由实际浏览器截取，不冒充已实现导出功能。

**停止点：提交三组构图与材质验收记录，确认后再进入交互开发。**

## 五、阶段四：核心交互与动画闭环

### 目标与前置条件

阶段三通过后，用简洁操作面板实现从闭合、开盖、耳机取出到归位和关盖的完整操作闭环。

### 开发任务与文件

1. 创建 `src/interaction/state.ts` 和 `src/tests/state.test.ts`，先定义合法状态、事件和连续点击策略。
2. 创建 `src/interaction/controller.ts`，统一调度盒盖、耳机与相机动画。
3. 创建 `src/interaction/picking.ts`，处理盒盖点击及点击/拖拽区分。
4. 更新 `src/scene/cameraPresets.ts`、`src/ui/controls.ts`，实现视角切换、动作按钮与状态反馈。
5. 创建 `src/tests/controller.test.ts`，覆盖中途重置、重复事件和最终姿态。
6. 在实际浏览器中验证动作路径与边界操作，补充自动化用例至 `tests/e2e/interaction.spec.ts`。

### 可验收成果

- 可直接操作的开盖、关盖、取出、归位、预设视角和重置功能。
- 与当前状态一致的按钮文字和可操作状态。
- 完整流程的起止姿态截图及测试记录。

### 用户验收步骤

1. 按“开盖 → 取出 → 归位 → 关盖”完成一次操作。
2. 在取出途中点击重置，确认所有零件和相机恢复。
3. 快速重复点击同一按钮，观察是否出现动作叠加。
4. 拖动产品后松手，确认不会误触开盖。
5. 切换预设视角，再恢复自由旋转。

### 通过标准

- [ ] 完整操作循环连续执行 20 次，无明显穿模、位置漂移或卡死。
- [ ] 2 秒内快速触发同一操作 10 次，仍符合预定处理策略，不生成冲突动画。
- [ ] 在开盖、取出、归位和相机过渡期间分别重置，均能恢复一致初始状态。
- [ ] 耳机未归位时，关盖动作按设计拒绝或先归位，不直接压入耳机。
- [ ] 拖拽与点击区分可靠，相机过渡不会与手动控制争抢。
- [ ] 状态与控制器测试通过，正式界面不依赖开发调试开关。

### 本阶段不做

完整热点文案、最终移动端排版和高分辨率 PNG 导出。

**停止点：先验收核心动作可靠性，不以漂亮动画掩盖状态错误。**

## 六、阶段五：完整页面、热点与图片导出

### 目标与前置条件

阶段四通过后，将交互演示整理成可正式浏览的桌面与移动端页面，并完成实际图片导出。

### 开发任务与文件

1. 更新 `src/ui/controls.ts`、`src/ui/styles.css`、`index.html`，完成标题、工具栏和响应式布局。
2. 创建 `src/interaction/hotspots.ts`、`src/config/hotspots.ts`、`src/ui/detailsPanel.ts`，实现热点跟随、遮挡判断与说明面板。
3. 创建 `src/ui/status.ts`，展示加载、空内容、重试和降级提示。
4. 创建 `src/export/capture.ts`、`src/tests/capture.test.ts`，实现尺寸计算、导出和渲染状态恢复。
5. 生成项目自己的静态预览放入 `public/preview/`，用于加载与不可用状态。
6. 创建 `tests/e2e/page.spec.ts`，覆盖布局、键盘、热点与导出操作。

### 可验收成果

- 完整桌面页面和移动端布局。
- 可点击且带遮挡判断的产品热点与文字说明。
- 由页面按钮真实生成的 PNG 文件，长边为 2048px，不包含 HTML 工具栏。
- 桌面和移动视口的实际截图。

### 用户验收步骤

1. 在桌面尺寸下查看标题、产品、工具栏和说明面板。
2. 切换窄屏布局，操作按钮、旋转模型并滚动页面。
3. 点击热点并旋转产品，检查热点是否正确隐藏或跟随。
4. 使用 Tab 和键盘操作核心按钮。
5. 调整到任意视角，点击导出并打开下载的 PNG。

### 通过标准

- [ ] 至少在 `1440 × 900` 与 `390 × 844` 两个验收视口下，主体和操作区可用，无非预期横向滚动。
- [ ] 模型与工具栏不互相遮挡关键内容，说明卡不会覆盖无法关闭的操作区。
- [ ] 热点随部件移动，被模型遮挡或移到视口外时合理隐藏。
- [ ] 核心操作可由键盘完成，焦点可见；减少动态效果设置有效。
- [ ] 移动布局中可区分模型操作和页面滚动；真实触摸设备验证在阶段六完成，不能仅以模拟视口宣称通过。
- [ ] 实际 PNG 文件可打开，长边恰为 2048px，内容不是黑图或空白图，与当前产品姿态一致。
- [ ] 导出后交互和画面尺寸恢复正常；连续导出 5 次不破坏场景状态。
- [ ] 加载和失败提示可见，缺少热点文案时不显示空面板。

**停止点：提交完整页面与实际导出图片，验收后进入最终优化。**

## 七、阶段六：性能、兼容、异常与最终交付

### 目标与前置条件

阶段五功能验收通过后，不再新增首版功能，集中完成性能优化、兼容性测试、异常处理和交付文档。

### 开发任务与文件

1. 创建 `src/scene/quality.ts`，根据实测设置像素比、阴影和材质质量档位。

### 可验收成果

- 能成功构建并本地预览的生产版本，以及 `dist/` 构建产物。
- 性能测量记录、浏览器/设备测试矩阵和异常测试记录。
- 安装、启动、构建、参数调整与已知限制说明。
- 前五阶段功能的完整回归结果。

### 性能验收方法

- 记录设备型号、GPU、系统、浏览器、视口、像素比和画质档位。
- 页面预热约 10 秒后，分别测量旋转与动作演示场景至少 30 秒。
- 记录中位帧时间、P95 帧时间和明显卡顿，不用瞬时 FPS 截图代表全部性能。
- 在已约定的参考设备上，以桌面中位帧时间不高于约 18.2ms（约 55 FPS，目标接近 60 FPS）、移动端不高于约 33.3ms（约 30 FPS）作为初始验收线。
- 如果设备本身刷新率、节能模式或软件渲染影响测试，记录条件并重新约定测试环境，不隐瞒或更改结果。
- 无头浏览器用于回归和截图；不能单独代表真实 GPU 与手机性能。

### 用户验收步骤

1. 按 README 从已安装依赖或干净安装环境启动生产预览。
2. 完成一次全部核心功能操作，并打开导出的图片。
3. 在约定真实手机上验证旋转、点击、滚动和屏幕方向变化。
4. 查看性能报告和浏览器测试矩阵。
5. 查看模拟失败状态下的静态降级和重试演示。

### 通过标准

- [ ] 类型检查、单元测试、生产构建和主要浏览器回归通过。
- [ ] 在约定参考设备与画质档位上达到性能验收线；未达标则修复或明确由用户批准调整目标。
- [ ] Chrome、Edge、Safari 和至少一台真实手机的验证结果已记录。
- [ ] 缺少设备或工具时标记为未验证；若无用户明确接受该限制，不能宣称跨平台最终验收通过。
- [ ] 资源加载失败或 WebGL 不可用时不出现无提示白屏，静态预览与必要说明可用。
- [ ] 上下文恢复失败时能够提示重试或降级。
- [ ] 多次初始化和销毁后，应用持有的几何、纹理和事件监听数量不单调增长；不要求渲染器内部缓存计数绝对为零。
- [ ] README 可用于复现启动与构建，素材来源和许可记录完整。
- [ ] 用户确认最终视觉、交互和已知限制。
